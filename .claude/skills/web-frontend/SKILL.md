# PrepperBox.Web frontend

React 19 + TypeScript SPA. State via Redux Toolkit + redux-saga (+ redux-persist). UI with PrimeReact (theme `viva-dark`). Bundled by Vite. Tested with Vitest. Shared building blocks come from the private `@hwndmaster/atom-*` packages.

**Package manager is `pnpm`** (pinned `pnpm@10.33.0`). Never use `npm` or `yarn`. All commands run from `PrepperBox.Web/`.

## Commands

| Task                  | Command (cwd = `PrepperBox.Web`)            |
| --------------------- | ------------------------------------------- |
| Install deps          | `pnpm install`                              |
| Dev server            | `pnpm start` (port 5096, opens browser)     |
| Dev server (Aspire)   | `pnpm start:aspire`                         |
| Build                 | `pnpm build`                                |
| Lint                  | `pnpm lint` (eslint, cached)                |
| Test (watch/run)      | `pnpm test`                                 |
| Test + coverage       | `pnpm test:coverage` → `coverage/lcov.info` |
| Regenerate API client | `pnpm nswag` (WebApi must be running on port 5095 — it reads `http://localhost:5095/openapi/v1.json`) |

After any change, run **`pnpm lint`** and **`pnpm test`** before considering it done. The build also typechecks.

The backend API runs on port 5095 (`VITE_API_URL` in `.env`); production relies on the nginx same-origin `/api/` proxy instead.

## Project layout (`src/`)

- `api/` — generated HTTP client. `api.generated.ts` is **generated by NSwag from the WebApi** (config in `nswag/webapi.nswag`) — never hand-edit it; run `pnpm nswag`. `apiAxios.ts` wires the singleton axios client; `setup.ts` configures it; `converters/` convert between API DTOs and app models (one per domain), `fieldMapping/` adapts field names from backend (C#) to app DTO's field names when processing validation errors from the server.
- `store/` — one folder per domain slice (`categories`, `consumptionLogs`, `openFoodFacts`, `products`, `storageLocations`, `trackedProducts`). `setup.ts` builds the store via `createAppStore` from `@hwndmaster/atom-react-redux` with **redux-persist** (`persistKey: "root"`) — bump `persistVersion` when changing the shape of persisted state. `setupSagas.ts` registers sagas; `appState.ts` is the root state.
- `components/` — reusable UI (`layout/Layout`, `productForm`, `trackedProductForm`, `editCategory`, `editStorageLocation`, `editProductFamily`). Forms use `react-hook-form` + zod schemas (in `schemas/`) via `@hookform/resolvers`.
- `pages/` — route-level screens. Routing via `react-router-dom` v7 in `RootComponent.tsx`.
- `models/` — app-side types per domain + `types.ts` (reference-type factories) + primitives.
- `schemas/` — zod form-validation schemas, one per entity (`<entity>Schema.ts` exporting `<Entity>SchemaData`); wired to forms via `react-hook-form` + `@hookform/resolvers`.
- `shared/` — `constants.ts`, `routes.ts`, `loadingTargets.ts`, domain helpers.
- `utils/` — general utilities; `utils/tests/` holds shared test fakes (`fakeAxios.ts`, `fakeStore.ts`).
- `styles/` — global SCSS (`main.scss`, `_variables.scss`, `_mixins.scss`, …); variables/mixins are auto-injected into every SCSS module by `vite.config.ts`.
- `telemetry/` — OpenTelemetry setup (`setupOpenTelemetry.ts`), called once from `index.tsx`.
- `primereact.ts` — barrel re-exporting every PrimeReact component in use; import PrimeReact components from here, not from `primereact/*` directly.
- Specialities: `react-zxing` for barcode scanning, `recharts` for charts.

## Store slice pattern (Redux Toolkit + saga)

Each slice folder has a fixed file set — follow it exactly when adding a slice:

- `state.ts` — the slice's state interface.
- `actions.ts` — **public** actions, the only ones other modules dispatch.
- `actionsInternal.ts` — **internal** actions dispatched only by sagas/reducers within the slice.
- `reducers.ts` — `createReducer` over `actionsInternal`.
- `sagas.ts` — `function*` sagas using `redux-saga/effects` and `callApi` from `@hwndmaster/atom-react-redux`; call the API via `apiClient().<client>.<method>()`, use converters from `/api/converters`.
- `selectors.ts` — selectors over the slice state (use `typedSelect` in sagas).
- `messages.ts` — re-imports from `api/`.
- `index.ts` — re-exports `* as Actions` and `type * as State`.
- `*.test.ts` — reducer and saga tests colocated.

## Action creators

* Use `createAction` from `@reduxjs/toolkit` for simple scenarios.
* Use `createActionWithMeta` from `@hwndmaster/atom-react-redux` when the caller must handle the result (error toast on rejection, redirect on success).
* Use `createActionWithMetaValidatable` when the saga result may contain a validation result (form submissions).

## Wrappers in sagas

* Use `withLoading` to block a part of the UI, where the part is defined via `LoadingTargets`.
* Use `withCallback` to handle actions created using `createActionWithMeta`.
* Use `withValidatableCallback` to handle actions created using `createActionWithMetaValidatable`.

## Server validation errors

Field-level validation errors from the server are surfaced on the matching form fields end-to-end:

* the create/update **action** is `createActionWithMetaValidatable<Req, Ref, XSchemaData>`;
* the **saga** wraps its work in `withValidatableCallback(meta, { mapValidationField }, …)` using the domain's mapper from `api/fieldMapping/` (which maps C# PascalCase field names to zod schema field names);
* the **form** passes `translateErrorsToForm(form)` on submit. Forms are "dumb" (the parent page dispatches the action), so they forward the translator through their `onSubmit`/`onSave` callback; a form that dispatches directly passes it inline.

## Architectural boundaries (enforced by ESLint `import-x/no-restricted-paths`)

These are hard rules — violating them fails lint:

- The `api/` folder may **only** be imported from `store/` (test fakes under `utils/tests/` are exempted via an ESLint override).
- Within a slice, only `sagas.ts` and `messages.ts` may import from `api/`.
- `actionsInternal.ts` may only be imported within `store/`.
- `sagas.ts` may only be imported within `store/`.

So: UI (`components/`, `pages/`) dispatches **public** actions and reads state via selectors; it never touches `api/` or `actionsInternal` directly.

## Testing conventions

- Vitest with `globals: true` (no need to import `describe`/`it`/`expect`), `jsdom` environment, `setupTests.ts` setup file.
- Tests are colocated as `*.test.ts(x)` next to their target source file (e.g. `src/shared/loadingTargets.test.ts`, `src/api/fieldMapping/helpers.test.ts`). Shared test fakes live in `src/utils/tests/`: `fakeAxios.ts` (mock HTTP via `@hwndmaster/atom-testing-utils`) and `fakeStore.ts`.
- Coverage uses the `v8` provider (`@vitest/coverage-v8`) and emits `text` + `lcov` into `coverage/` — `coverage/lcov.info` is the machine-readable report. `coverage/` is git-ignored. Config lives in `vitest.config.ts`; `*.test.ts(x)` and `src/**/tests/**` are excluded from the measured sources.
- Use the `@/` path alias for `src/` imports.
- Follow the **Arrange / Act / Assert** comment structure.
- **ALWAYS** select screen elements by their `data-test_id` attributes in tests. If an element is missing one, add it to the component. Format: `ComponentName__Element_Description`, e.g. `ProductForm__Submit_Button`. Avoid selecting by content text.
- Use the reference-type factories from `models/types.ts` (e.g. `categoryRef(1)`) instead of primitives when creating test data.
- When testing a specific function (reducer/action/etc.), name the test `functionName: description of the test case`.
- Do NOT write exhaustive test suites — cover rendering, main logic, standard business scenarios, and the most likely edge cases.

### Saga tests

Each slice has a colocated `sagas.test.ts`. The pattern:

- Drive the saga with `SagaRunner` from `@hwndmaster/atom-testing-utils`, typed as `new SagaRunner<AppState>()`, and run it with `await sagaRunner.runSaga(mySaga, action)`.
- Mock HTTP with the shared `fakeAxios` from `@/utils/tests/fakeAxios` — `fakeAxios.setupGet(api.CategoriesClient, "categoriesAll").reply(200, [...])`, plus `setupPost` / `setupPut` / `setupDelete`. The operation name is the generated client method; route parameters must be supplied (`setupDelete(api.CategoriesClient, "categoriesDELETE", { id: categoryRef(4) })`) or the URL will not match. Passing `{ body: request }` additionally asserts the request payload.
- **Reset both in `beforeEach`**: `fakeAxios.reset()` and `sagaRunner.reset()`. `reset()` does *not* clear the initial state, so also re-seed it with `sagaRunner.setInitialState(...)`.
- Sagas reading the store via `typedSelect` need `sagaRunner.setInitialState({ categories: { categories: [existing] } })` — only the slices the saga selects from.
- Assert store updates with `sagaRunner.findDispatchedAction(actionsInternal.setCategory)`, which returns the payload.
- Assert `withLoading` via `expect(sagaRunner.dispatched).toContainEqual({ type: Common.Actions.showLoader.type, payload: LoadingTargets.Categories })`. Do **not** pass `Common.Actions.showLoader` to `findDispatchedAction` — its prepared payload type does not match and it fails to typecheck.
- Cover `withCallback` / `withValidatableCallback` outcomes by passing the meta callbacks straight into the action creator and spying on them: `actions.createCategory(request, validationReject, resolve, reject)` and `actions.deleteCategory(id, resolve, reject)`. Use `vi.fn<(reason?: string) => void>()` so the mock stays typed.
- Saga tests may import from `api/` — the ESLint `no-restricted-paths` zone explicitly exempts `sagas.test`.

## Conventions

- Indentation: 4 spaces; double-quoted strings (matches existing files and stylistic config).
- Prefer PrimeReact components (via the `src/primereact.ts` barrel) and the `@hwndmaster/atom-react-*` helpers over hand-rolling.
- Validation schemas use `zod` (v4) under `schemas/`, wired to forms via `react-hook-form` + `@hookform/resolvers`.
- Avoid conversion like `as unknown as Type` or `as unknown as never` unless absolutely necessary — restructure types instead.
- Import order in a React component file:
  1. React and related libraries
  2. Third-party libraries
  3. `@hwndmaster/atom-*` packages
  4. Application-wide imports, with the following order:
     - Store imports (e.g., `import { RootState } from "@/store";`)
     - API imports (e.g., `import * as api from "@/api/api.generated";`)
     - Model imports (e.g., `import { BuddyInfo } from "@/models/buddyInfo";`)
     - Utility imports (e.g., `import { formatDate } from "@/shared/dateUtils";`)
     - Component imports (e.g., `import { FormInputText } from "@/components/forms";`)
  5. Components from upper folder (e.g., `import AnotherComponent from "../anotherComponent";`)
  6. Local imports (e.g., `import AnotherComponent from "./anotherComponent";`)
  7. Styles (e.g., `import "./myComponent.module.scss";`)

## CSS Styling

- Always use SCSS Modules or `main.scss`; stack styles in layers (component / feature / global).
- Use camelCase for CSS class names; access them as `styles.myClassName` (no bracket notation).

## Naming conventions

- PascalCase for type names and constants (`const MaxUsers = 100;`), camelCase for variables and functions — per the `@typescript-eslint/naming-convention` rules in `eslint.config.js`.

## Atom-web packages

- Packages under the `@hwndmaster` scope are called atom-web packages.
- If you need to change any atom-web package, ask first, then make the change. Afterwards ask for the new versions to be published and continue; if publishing is deferred, assume the published versions will contain your changes and proceed without waiting.
